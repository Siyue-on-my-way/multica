# 业务上传数据生命周期管理（SIY-153）

## 1. 背景与现状

`docker/volumes/backend_uploads`（容器内 `/app/data/uploads`，由 `LOCAL_UPLOAD_DIR` 控制）保存全部用户上传文件，当前约 212MB / 1200+ 个文件。它是业务数据而非构建缓存，因此不能像 Docker 缓存那样无差别回收 —— 只能依据**数据库引用**与**保留期**做生命周期管理，**绝不允许按文件年龄直接删除**。

本机基线（2026-09-07 实测）：

| 指标 | 数值 |
| --- | --- |
| 磁盘对象（不含 sidecar） | 606 个 / 约 204MB |
| 数据库引用 key | 603 个 |
| 无引用且过宽限期（可清理） | 3 个对象 + 3 个 sidecar，约 970KB（均为被替换的旧头像） |
| 被引用但文件缺失 | 0（引用完整性完好） |

结论：当前占用几乎全部是**有引用的活跃业务数据**；清理脚本的价值在于堵住"孤儿文件只增不减"的增长口子，而不是立刻释放大量空间。

## 2. 上传目录数据清单

| 前缀 | 内容 | 写入方 | 数据库引用 |
| --- | --- | --- | --- |
| `workspaces/<ws>/<uuidv7>.<ext>` | issue / 评论 / 聊天附件 | `handler/file.go` 上传接口 | `attachment.url` |
| `workspaces/<ws>/source-context/<uuid>.<ext>` | 上下文快照克隆 | `handler/source_context.go` | `attachment.url`（`source_context_id` 行）+ `issue_source_context_object_intent` 台账 |
| `workspaces/<ws>/<slack\|wecom\|lark\|dingtalk>/<inst>/<sha256>` | IM 渠道媒体 | `integrations/*` | `attachment.url` + `channel_media_pending_object` 台账 |
| `users/<user>/<uuidv7>.<ext>` | 头像（user/agent/squad/workspace）及无工作区上传 | `handler/file.go`、`handler/avatar.go` | 四类 `avatar_url` 列、`attachment.url` |
| `skills/` | 技能收件箱（投递→导入→删除，失败进 `failed/`） | `handler/skill_inbox.go` watcher | 无（自带生命周期，自清理） |
| `*.meta.json`（sidecar）、`.<key>.tmp`（写暂存） | 本地存储实现细节 | `internal/storage/local.go` | 跟随其对象文件 |

## 3. 数据库引用关系（清理判定依据）

引用提取规则与后端 `LocalStorage.KeyFromURL` 一致：URL 取 `/uploads/` 之后的部分（key 永远是服务端生成的 UUID/hex 路径，不会包含 `/uploads/`）。台账表存的是原始 key。

**引用集合 SQL（`scripts/uploads-gc.sh` 内置，维护时同步更新）：**

```sql
SELECT DISTINCT k FROM (
  SELECT substring(url FROM '/uploads/(.*)$')        FROM attachment WHERE url LIKE '%/uploads/%'
  UNION
  SELECT substring(avatar_url FROM '/uploads/(.*)$') FROM "user"    WHERE avatar_url LIKE '%/uploads/%'
  UNION
  SELECT substring(avatar_url FROM '/uploads/(.*)$') FROM agent     WHERE avatar_url LIKE '%/uploads/%'
  UNION
  SELECT substring(avatar_url FROM '/uploads/(.*)$') FROM squad     WHERE avatar_url LIKE '%/uploads/%'
  UNION
  SELECT substring(avatar_url FROM '/uploads/(.*)$') FROM workspace WHERE avatar_url LIKE '%/uploads/%'
  UNION
  SELECT storage_key FROM channel_media_pending_object
  UNION
  SELECT storage_key FROM issue_source_context_object_intent
) refs WHERE k IS NOT NULL AND k <> '' AND position('..' IN k) = 0;
```

要点：

- **attachment 表是绝大多数对象的引用方**。聊天、渠道媒体、上下文克隆最终都会落一行 `attachment`。
- **两个意图台账（intent ledger）的所有状态都算引用**（`pending`/`deleting`/`tombstoned`）。渠道媒体与上下文克隆的对象删除由各自的 reconciler/sweeper 异步负责（含崩溃恢复与迟到写入的再删除），清理脚本永不越权处理台账内的 key。
- 头像列可能存 emoji 标记或外部 URL，SQL 中的 `LIKE '%/uploads/%'` 已过滤。

**孤儿（无引用文件）产生的路径 —— 这些就是磁盘持续增长的原因：**

1. 评论 / issue / 聊天会话 / 工作区被级联删除时，`attachment` 行随 FK 级联消失，但存储对象没有对应的删除路径；
2. 上传成功但 `CreateAttachment` 建行失败（接口仍返回 link，文件已落盘）；
3. 头像更换：`avatar_url` 直接 UPDATE，旧头像文件无人删除；
4. 进程崩溃留下的 `.<key>.tmp` 写暂存；
5. 渠道媒体 reconciler 覆盖不到的历史残留。

## 4. 保留期策略

**删除必须同时满足两个条件，缺一不可：**

1. **数据库无引用**（第 3 节的引用集合完全查不到该 key）；
2. **文件修改时间早于宽限期**（默认 `14d`，`UPLOADS_GC_GRACE` 可调）。

宽限期的意义 —— 它同时覆盖：

- 在途上传竞态：文件先落盘、数据库行后建（毫秒~秒级），宽限期 > 0 即安全；
- 最近误删的恢复窗口：配合每日备份，14 天内任何被删对象都可从备份找回；
- 未知/缓慢的引用建立方（如客户端重试）。

**取值建议：宽限期 ≥ 2 × 备份周期。** 每日备份 + 14 天宽限期意味着任何被清理的文件至少存在于 14 份备份中。

**永不删除的部分：**

- `skills/` 收件箱目录（watcher 自带完整生命周期，含失败隔离区）；
- 台账表（任意状态）中的 key；
- 引用查询无法完成时的所有文件（见第 6 节安全机制）；
- 白名单之外（`users/`、`workspaces/` 之外）的一切未知前缀 —— 只报告不删除，防止未来新增上传生产者时被误清。

## 5. 备份策略

上传目录与数据库**必须成对备份、成对恢复**（引用在数据库里，内容在上传目录里，单独恢复任何一半都会造成引用悬空或孤儿）：

1. **每日** `pg_dump`（引用与元数据）+ 上传目录增量备份（rsync/restic 均可，content-only）；
2. 备份保留 **14 天**（与宽限期对齐：任何被 GC 删除的文件，其内容至少存在于 1 份备份中，误清可回捞）；
3. 恢复顺序：先恢复数据库，再恢复上传目录，最后跑一次 `uploads-gc.sh` 对账（"被引用但文件缺失"应为 0，不为 0 说明备份不完整）。

## 6. 清理脚本：`scripts/uploads-gc.sh`

```bash
# 默认 dry-run：只报告，不删除（restart.sh 每次重启自动跑一次报告）
./scripts/uploads-gc.sh

# 确认报告无误后执行删除（仍受"无引用 + 过宽限期"双条件约束）
./scripts/uploads-gc.sh --apply

# 常用环境变量
UPLOADS_GC_GRACE=14d ./scripts/uploads-gc.sh            # 调整宽限期
UPLOADS_DIR=/path/to/backend_uploads ./scripts/...      # 指定上传目录
```

数据库连接自动解析：优先环境变量 `DATABASE_URL`，否则读 `docker/.env`；宿主机 `psql` 不可用时自动 `docker exec` 一个 postgres 容器（按端口映射匹配）。特殊部署可用 `UPLOADS_GC_PSQL` 直接指定命令。

**安全机制（多层）：**

| 机制 | 说明 |
| --- | --- |
| 默认 dry-run | `--apply` 才删除；restart.sh 挂载的是报告模式，重启路径永不删除 |
| 引用信封校验 | 引用查询必须返回 `refs-begin`/`refs-end` 信封；DB 不可达、输出异常（含被 mock 的假成功）一律中止且不删除 |
| 双条件删除 | 无引用 **且** 过宽限期；引用查询失败 = 零删除 |
| 白名单 | 只纳管 `users/`、`workspaces/`；`skills/` 与未知前缀永不触碰 |
| 路径约束 | 删除路径全部由 `find` 相对路径推导，位于 `UPLOADS_DIR` 内 |
| flock 防并发 | 同时只允许一个实例 |

**周期执行建议（crontab，可选）：**

```cron
# 每天凌晨对账 + 清理（dry-run 先行一周期观察报告后再开 --apply）
0 4 * * * cd /path/to/multica && ./scripts/uploads-gc.sh --apply >> logs/uploads-gc.log 2>&1
```

## 7. 验证方式（对照验收标准）

1. **策略文档化** —— 即本文档；
2. **准确识别无引用且过期的文件** —— `scripts/uploads-gc.test.sh`（mock psql + 夹具目录）覆盖：引用保留、宽限期保护、孤儿三件套删除、DB 失败中止、假成功中止、非纳管目录保护；本机 dry-run 实测识别出 3 个被替换的旧头像，与手工对账一致；
3. **有引用的业务数据完好无损** —— 脚本每次运行都对账"被引用但文件缺失"计数（清理前后均应为 0）；执行清理后用第 3 节 SQL 复查引用集合、抽查附件可下载。

## 8. 维护注意事项

- **新增上传生产者**（新的 key 前缀或新的引用表）时：若前缀在 `users/`/`workspaces/` 之外，需加入 `uploads-gc.sh` 白名单；引用列/表需同步加入第 3 节 SQL —— 否则新数据要么被误清（危险），要么永远不清理（安全侧）。
- 头像、渠道媒体、上下文克隆的对象删除若在后端补齐同步删除路径（handler 内 `Storage.Delete`），孤儿增速会进一步下降，GC 退化为兜底。
- 若部署切换到 S3 存储（`S3_*` 配置），本地目录语义不变，但清理脚本需另行适配 S3（当前仅支持本地盘）。

# Self-hosted CLI download channel

This directory is bind-mounted read-only into the nginx container and served
at `http://<server-host>:<port>/downloads/`. It exists because the CLI/daemon
updater targets the official `multica-ai/multica` releases by default (the
fork's own builds are unreachable there), so a fork deployment must serve its
own binaries for first install and manual bootstrap.

Contents (regenerated by `scripts/publish-cli-downloads.sh`):

| file | purpose |
|---|---|
| `multica-linux-amd64` | fork CLI binary, Linux x86_64 |
| `multica-darwin-arm64` | fork CLI binary, Apple Silicon |
| `multica-windows-amd64.exe` | fork CLI binary, Windows x86_64 |
| `checksums.txt` | SHA-256 manifest, verified by the installers |
| `manifest.json` | channel / version / commit metadata |
| `install.sh` | one-click installer, macOS/Linux: `curl -fsSL <base>/install.sh \| bash` |
| `install.ps1` | one-click installer, Windows: `irm <base>/install.ps1 \| iex` |

The binaries themselves are **not committed** (reproducible from the checkout);
the installers, checksums and manifest are committed so the served channel
state stays auditable. Re-publish after every change that touches the
CLI/daemon:

```bash
scripts/publish-cli-downloads.sh
```

Once a fork GitHub release is published (e.g. `v0.4.41-siyue.1`) and the
machine has `MULTICA_UPDATE_REPO` set, upgrades flow through
`multica update` / `multica runtime update` instead of this channel.
